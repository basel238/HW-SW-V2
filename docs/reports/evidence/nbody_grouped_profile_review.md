# Latest nbody grouped profile and source audit

Read-only audit of `nbody_baseline_20260920-015849` and `nbody_optimized_20260920-020900`. Runtime/PMU-stat evaluation belongs to the main review; this note concerns native sampling, cProfile, and source interpretation.

## Matched work and profiler limitations

Both native perf-record logs explicitly execute 5 loops × 20,000 steps = 100,000 timesteps and 1,000,000 pair interactions, yielding the same final energy `-0.1690798593916718`. Optimized log explicitly says `kernel=grouped`. Both use `python3-dbg`, cycle-period sampling at 5,000,000 cycles, DWARF unwinding with 8,192 stack bytes. Native profile total samples: 1,178 versus 1,120, a 4.9236% reduction. These are NOT the release-runtime measurements or an exact runtime reduction.

Both cProfile artifacts explicitly execute 1 loop × 20,000 steps and yield energy `-0.16908926275527172`. `advance` and `advance_grouped` are each called once. `_group_consecutive_pairs` is called once by grouped, making ten append calls; it does not rebuild groups every timestep. Its observed cProfile cumulative time is only 8.123 microseconds, but tracing timing is not a performance comparison metric. Whole-process call counts 4,911→5,926 reflect wrappers/import/argument-parsing differences and do not establish inner-loop call overhead.

The native reports list zero lost samples, but 24 baseline and 31 optimized samples contain an unknown ancestor. Leaf counts remain generally useful; perfect unwinding is not established. The measured git commit is 2d5f5e5 with a dirty working tree, and the manifest does not hash the optimized source. The logs prove grouped selection, not exact reproducibility from that commit alone.

## Why this matches what grouped actually removes

Upstream already unpacks positions into locals for each pair. Grouped retains first-body position and velocity across four groups of lengths 4, 3, 2, 1. Second-body velocities still read/write their lists for each pair; all position updates still happen after all ten pair interactions.

The saved `component_breakdown.json`, generated by `component_breakdown.py`, independently instruments one timestep using list subclasses, separating explicit subscripting and sequence-unpack component reads. It collects no timing, preserves all 30 resulting state components bit-for-bit, and changes no repository file.

|Per-timestep component operation|Upstream|Grouped|Reduction|
|---|---:|---:|---:|
|Explicit indexed reads|75|45|40%|
|Components read through unpacking|75|69|8%|
|All component reads|150|114|24%|
|Explicit indexed writes|75|57|24%|
|All component accesses|225|171|24%|

The 40% indexed-read decrease is closer to the observed 35.7% GetItem sample decrease; the 24% writes decrease is close to the observed 22.9% SetItem sample decrease. These comparisons are qualitatively strong, not equal metrics. CPython sequence unpacking does not have the same execution path or cost as general subscript reads. The full logical-access 24% count must not be treated as a reduction of runtime or native instructions.

The source still computes the same pair arithmetic, power, and drift. Python local variables hold references to boxed floats, not guaranteed machine-register doubles. Arithmetic still allocates result floats and updates references. Only selected list round trips disappear.

## Extra recurring work and residual costs

Grouped adds a nesting level: baseline sets up two list iterators per timestep (pairs and bodies); grouped sets up six (groups, four partner lists, and bodies). This adds 80,000 list-iterator setups per 20,000-step unit, plus corresponding iteration/termination work. It is different from constructing the four groups once per advance call. Native inclusive list_iter samples increase 5→18, listiter_dealloc 7→24, and self listiter_next 6→10. Those low counts are consistent with extra iterator work but cannot quantify its release cost.

Other potential offsets are local loads/stores and reference management around group entry and writeback. No claim that the whole benefit is lost to the helper's one-time grouping is supported. No cache-bandwidth diagnosis follows from list access overhead: these are Python container operations over a very small fixed state.

## Flame graph appearance and top-30 traps

- Both SVGs stretch to a full-width canvas. Smaller total native sample count does not make a visually narrower graph.
- Both kernels remain Python loops performing the same arithmetic. Native eval, numeric dispatch, float creation/reclamation, and residual list paths remain present.
- Optimized wrapper calls through `_run`, `benchmark`, and `functools.partial`. Its additional stack ancestry increases weighted average depth from 41.48 to 51.91 frames, without demonstrating any extra per-pair Python calls.
- Baseline's leading top30 Eval stack has 528 samples. Optimized Eval is split among two major stacks of 378 and 102 samples because the partial/vectorcall ancestry differs. Aggregate all folded leaves: 531→482. Comparing 528 only with 378 overstates the reduction.
- Top30 coverage is 995/1178=84.47% versus 827/1120=73.84%, so the optimized top30 excludes a larger fraction. Full folded data is necessary.
- The files named python.folded merely retain native stacks containing Python-related symbols; they do not recover source-level Python function names.
- Sampled stack depth is simultaneous nesting, not the total number of repetitions. Height is not a useful optimization-success metric.

## Next experiment justified by these data

More complete local-state reuse is a reasonable next isolated variant: all five bodies' position/velocity state in locals across timesteps, ten pair interactions in canonical order, write state back at advance return. It targets remaining list traffic and can also remove the grouped nested iteration. This is a stronger fixed-five-body specialization, not a proven speedup. Preserve each floating-point expression and per-component update order, validate all 30 state components and energy over the actual multi-loop workload, and retain the grouped result as its own experiment. Fully local Python still retains boxed-float arithmetic and interpreter execution; it is not an unboxed numerical kernel.
